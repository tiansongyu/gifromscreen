# WPF vector rendering: explicit new-path work

This follows the [first native vector acceptance and failing pixel gate](VECTOR-SHAPE-QA-2026-09-09.md).
The existing saved `VectorShape` version 1 and legacy `Shape` renderer remain
unchanged. A new geometry API is being validated before choosing an explicit
persisted rendering version; loading a project never implicitly upgrades pixels.

## Geometry and layout

`wpf_vector_shape_geometry` derives the fixed 96-DPI reference's *RenderedGeometry*
contour. It is not a promise that the contour alone includes every visible clip.
The independent layout module derives actual offset, RenderSize and optional
local layout clip from requested values, using bounded fixed-size polygon math.

Rectangle/Ellipse arrange from the rounded dimensions and stroke natural size.
Triangle/Arrow retain their original requested vertices, but their stroke bounds
can enlarge actual RenderSize and therefore the relative rotation center.
Native float32 boundaries, ties-to-even layout rounding, miter truncation and
Arrow's explicit smooth joins are kept separate from pixel AA quantization.
The first seven real Windows layout observations match; further degenerate,
overscan and tiny-size tests are source-derived, not substitutes for new pixels.

The reference now retains nineteen complete input fixtures within the unchanged
64 KiB definition bound. It adds white/transparent fill and stroke probes and
four extreme-layout probes without changing earlier fixture values. Windows
logs include actual descendant bounds and `VisualTreeHelper.GetClip` geometry.

## Coverage evidence

Actual Windows run [34307669929](https://github.com/tiansongyu/gifromscreen/actions/runs/34307669929)
generated the first three dedicated fill probes. Local strict replay using the
new arranged geometry and the existing `ink_raster` matches **all original
premultiplied bytes** for integer triangle, fractional triangle and ellipse.
Reference: `/tmp/gfs-wpf-coverage-d1ba41e`; independent report:
`/tmp/gfs-wpf-fill-layout-d1ba41e/fill-coverage.json`.

This is explicitly a **filled-contour-only** gate. The complete project
comparator still fails and is not replaced by it. Its separate CI result and
artifact never turn a failing full comparison into success. No expected bytes
are generated by the Rust renderer, and reference pixels are not fed back into
its geometry calculation.

The reused rasterizer preserves the pinned WPF 28.4 half-up coordinate boundary,
integer HFD curve flattening and 8×8 coverage count. PM channel scaling uses
`(channel * coverage * 4 + 128) >> 8`, not a separately rounded A8 mask followed
by `/255` multiplication. Layout rounding and raster rounding are different.

## Candidate stroke and clip implementation

Native rectangle widening has a dedicated compact path. It expands/shrinks the
original radii before independent axis clamping; widening an already flattened
rounded rectangle is not equivalent. Triangle uses truncated miter10 joins;
the original Arrow declares smooth joins, which force round corners. Ellipse
widening needs the native double-precision flattener's position **and tangent**,
not the filled-path integer HFD or tiny-skia's default miter behavior.

Automatic WPF layout clipping also has a separate PM boundary. For the pinned
software PBGRA target, native layer creation falls back to a transparent
intermediate: fill and stroke composite first, then the mask draws that bitmap
back onto its parent without PNG/WIC in between. A geometric intersection of
each individual primitive with the mask would be a different operation. We
discarded an unconnected experimental intersection API after verifying this
source path; it was never applied to saved projects or used to claim parity.

The layout module exposes clip geometry without claiming how it is composited.
Stroke preparation and bounded PM clip rendering are now implemented in a
separate batch entrypoint. Unclipped shapes paint fill/stroke **directly onto
the existing canvas**; only clipped visuals receive their own PM intermediate.
Initially rendering every shape to its own bitmap produced 23 differing pixels
in the two-shape fixture (channel differences up to 2). That failed report is
retained at `/tmp/gfs-wpf-vector-candidate-4e28a35/vector-candidate.json`.

After preserving the actual native grouping, **all 14 complete vector cases**
from real producer run [34309842487](https://github.com/tiansongyu/gifromscreen/actions/runs/34309842487)
match exactly on explicit Rust 1.98.0 and 1.88.0. This includes fractional
fill/stroke, rounded-axis clamping, rotated triangle/arrow/ellipse, and all four
extreme layout/clip cases. Their 19 input stages also match; all remaining
non-vector artifacts are validated but are not mislabeled as candidate renders.
The 33 compared rows have zero RGBA differences. Both independent reports share
SHA-256 `6b42e00ecf6ff56bef686a2451318b89eecb0584bfbb0ce3e3b1912febb94301`:

- `/tmp/gfs-wpf-vector-batch-4e28a35.DEd3at/vector-candidate.json`
- `/tmp/gfs-wpf-vector-batch-msrv-4e28a35.WxiYXC/vector-candidate.json`

PNG pixels and raw RGBA must agree in addition to matching their separate
digests. A synthetic contradictory-envelope regression covers this check;
synthetic helper data are not WPF expected pixels.

The full persisted-V1 comparator remains separate and failing. This candidate
still needs broader production-scale coverage, a version-safe project/editor route,
larger/mixed-geometry cases and native acceptance before becoming the authoring
default. Existing saved V1 bytes and pipeline behavior are unchanged. The first
batch implementation conservatively divided a total 100M work bound between
phases. The next implementation consumes actual charged brush/raster/pixel work
across the whole batch and uses an explicit **250M** bound. Legacy V1 and Ink
default bounds remain 100M; there is no per-object multiplication of the new
batch allowance.
No release or full-project WPF parity is claimed by the 14-case result.

## Measured normal-size cases

The old 100M policy was measured before changing it: a 4K filled rectangle
barely fit, while a normal 4K rectangle with a 4px stroke exhausted its remaining
allowance. No resolution, shape, mask or expected pixel was changed to pass.
A test-only 500M measurement established the complete cost; the explicit new
250M default then passed all four cases in debug and release:

| Pure-render case | Charged work | Release seconds |
| --- | ---: | ---: |
| 1920×1080, two filled/stroked shapes | 41,181,530 | 0.05573 |
| 3840×2160, one full filled rectangle | 99,705,713 | 0.11936 |
| 3840×2160, full filled/stroked rectangle | 116,899,717 | 0.14437 |
| 3840×2160, rectangle + centered ellipse | 163,532,284 | 0.20790 |

Explicit Rust 1.98.0 release render-test binary:
`f3a20a2361494e6e7cdcc2c525e997baa4a2525cdaf195d87966ee33415333b9`.
The four-case process took 0.53 seconds wall time and 45,560 KiB peak RSS.
Evidence is under `/tmp/gfs-wpf-scale-500m.y1mRA9/`; separate old-100M failure,
test-only-500M measurement and formal-default-250M logs are retained.
These are **pure-render measurements**, not GIF encoding, recording FPS or an
isolated whole-application performance guarantee.

Both toolchains retain all 14 real candidate comparisons exactly after actual
metering and the new bound. Reports are
`/tmp/gfs-wpf-vector-meter250-1_98.tIeuV4/vector-candidate.json` and
`/tmp/gfs-wpf-vector-meter250-1_88.q39Y4V/vector-candidate.json`, both SHA-256
`90cacb08b8a46e3bd8db529c23146de8d9f31b54f0e84efc4e7d3e90112f0c9f`.
Many small objects on a large canvas still require scale validation and spatial
mask work; these four successful cases do not close that requirement.
